# Publisher Foundation V0 Design

## Scope

This slice implements the first two Publisher productization layers only:

- the Publisher module boundary and domain contracts;
- PostgreSQL persistence for accounts, immutable publish revisions, request state, attempts and external post references.

It does not implement Publisher API routes, Worker composition, scheduling UI, real platform adapters, metrics or credential resolution.

The Fake Platform adapter already exists and remains the contract-level test double. Real Douyin and WeChat Channels remain disabled.

## Boundary

Publisher owns `publisher_accounts`, `publisher_requests`, `publisher_request_revisions`, `publisher_attempts` and `publisher_external_posts`. It is the only module allowed to mutate these tables.

Project, Asset, Review and Job are consumed through their public services/contracts. No Publisher service reads another module's private tables directly.

The request aggregate stores mutable lifecycle state; revision and attempt rows are append-only histories. A request revision captures the asset checksum and publication metadata used for one immutable execution snapshot.

## Persistence

Migration `0009_publisher_foundation.sql` creates:

- `publisher_accounts`: logical platform account, credential reference, isolated profile key, capability snapshot and account status;
- `publisher_requests`: project/account aggregate, current revision, lifecycle state, stable idempotency key, retry metadata and correlation ID;
- `publisher_request_revisions`: immutable metadata and asset snapshot revisions;
- `publisher_attempts`: per-operation execution history linked to Job and Job Attempt IDs;
- `publisher_external_posts`: normalized external post identity with uniqueness protection.

All identifiers are text IDs generated by the application. Project and Job relationships retain foreign-key traceability. Secret-bearing values are intentionally absent from every table and JSON payload.

## State and invariants

Request statuses are `DRAFT`, `SCHEDULED`, `QUEUED`, `PUBLISHING`, `RECONCILING`, `PUBLISHED`, `FAILED` and `CANCELLED`.

- New requests are `DRAFT` and may receive new revisions.
- Scheduling requires a current revision and later API-level Review approval.
- A request has at most one active revision pointer and one active publication Job, enforced by a partial unique index on active Job idempotency keys at the application boundary.
- `UNKNOWN_EXTERNAL_STATE` requires `RECONCILING`; no direct retry is allowed.
- Attempts are historical rows; status fields may be finalized after a crash-recoverable attempt is created, but rows are never replaced.
- External post identity is unique per account and platform.

State transitions will be guarded in the Publisher service with row locks and an explicit transition table. Database checks protect enum values and non-negative counters; service logic protects transition ordering and cross-module validation.

## Idempotency and security

The request idempotency key is stable for the request lifetime. Repeated creation with the same key returns the existing aggregate. Revision changes do not change the request key.

Job payloads will contain only request/revision/project/correlation IDs. Credential references are resolved later inside the Worker boundary. Ordinary logs and diagnostics contain normalized failure codes and redacted metadata only.

## Verification

Contract tests cover bounded Publisher statuses and failure classifications. Database integration tests cover migration idempotency, constraints, append-only revisions, row traceability, request idempotency and external-post uniqueness. Existing 72-test regression suite must remain green.
